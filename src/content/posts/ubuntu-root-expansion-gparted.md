# 双系统下给 Ubuntu 根分区扩容 200GiB：一次完整的 GParted 实践

> 副标题：从 Windows E 盘划出 200GiB，到 Ubuntu 根分区扩展到 350G，完整记录方案选择、数据备份、Live U 盘制作、分区移动与结果验证。

2026.11.28

我的电脑装着 Windows 和 Ubuntu 双系统。Ubuntu 使用一段时间后，根分区逐渐紧张：清理缓存前，147G 的根分区已经用了约 108G；清理第一梯队缓存后，已用空间降到约 95G，可用空间回到 45G 左右。缓存清理能缓解眼前问题，但 Docker、开发环境和项目文件还会继续增长，所以我决定从 Windows 的 E 盘再划出 200G，真正扩大 Ubuntu 的可用空间。

这次的目标不是单独增加一个数据盘，而是把空间直接合并进 Ubuntu 根分区。最后根分区从 150G 扩展到 350G，没有重装 Ubuntu，没有重新格式化根分区，也不需要再次执行 `resize2fs`。这篇文章按实际操作顺序记录整个过程，也把中间遇到的下载失败、U 盘报错和备份校验问题一并写下来。

运行环境：Windows + Ubuntu 24.04 双系统 + GParted Live 1.8.1-6（amd64）+ ext4 / NTFS

## 一、先看清楚：磁盘、分区和挂载点不是一回事

开始之前，我先用 `lsblk`、`df -h` 和 `blkid` 确认设备关系。涉及分区操作时，不能只看“D 盘”“E 盘”这种 Windows 名称，必须落实到 Linux 设备路径。

```bash
lsblk
df -h
sudo blkid /dev/nvme1n1p4
```

我的机器里有两块物理 SSD：

- `nvme1n1`：放 Windows E 盘、Ubuntu EFI 分区和 Ubuntu 根分区，是这次要调整的磁盘。
- `nvme0n1`：其中有 Windows Data/D 盘，对应 `/dev/nvme0n1p4`，是另一块物理盘，后面用它保存备份。

在 Windows 中压缩 E 盘之后、运行 GParted 之前，`nvme1n1` 的关键布局如下：

| 设备或区域  | 大小   | 类型或用途          |
| ----------- | ------ | ------------------- |
| `nvme1n1p1` | 260M   | EFI 系统分区        |
| `nvme1n1p2` | 16M    | Windows 保留分区    |
| `nvme1n1p3` | 603.6G | NTFS，Windows E 盘  |
| 未分配空间  | 200GiB | 位于约 604～804GiB  |
| `nvme1n1p4` | 150G   | ext4，Ubuntu 根分区 |

根分区 UUID 为：

```text
2dad7864-2833-4414-af9f-41b1d914bdf8
```

这里最容易误解的一点是：Windows 里“压缩出了 200G 未分配空间”，并不代表 Ubuntu 已经自动获得了这 200G。未分配空间只是磁盘上的一段空白区域，只有把它合进现有分区，或者在其中建立新文件系统并挂载，Linux 才能真正使用。

## 二、方案选择：单独挂载 `/home`，还是合并根分区

最开始我考虑过两个方案。

方案一是把 200GiB 建成一个新的 ext4 分区，迁移 `/home`，再通过 `/etc/fstab` 自动挂载。方案二是不建立新分区，直接把原有的 `/dev/nvme1n1p4` 左移并扩大，让它吃下这段空闲空间。

两种方案在使用上的区别并不只是“操作步骤不一样”。

| 对比项     | 新分区挂载 `/home`                     | 直接扩展根分区                   |
| ---------- | -------------------------------------- | -------------------------------- |
| 空间使用   | `/home` 与其余系统目录分成两个空间池   | 整个根分区共享同一份空间         |
| Docker/apt | 仍然消耗根分区，不会自动使用新分区空间 | 可以直接使用扩容后的空间         |
| 文件移动   | 跨分区移动通常涉及实际复制             | 同一文件系统内移动通常只改元数据 |
| 挂载依赖   | 需要正确配置 `/etc/fstab`              | 仍使用原来的根分区挂载关系       |
| 操作风险   | 主要风险在数据迁移和挂载配置           | 需要移动分区，中断风险更高       |

我最终选择合并根分区，原因很具体：这台机器上的大文件不只在 `/home`。Docker、`apt` 安装的软件、`/var` 下的数据也会持续占用根分区。如果只给 `/home` 单独扩出 200G，就可能出现“`/home` 很空，但根分区仍然报警”的情况。

合并方案更符合我的使用方式，但它的代价是必须移动一个含有正在运行系统的分区，所以备份和 Live 环境都不能省。

## 三、为什么这次不是简单地“把分区往右拉大”

扩容前的结构可以简化成：

```text
[EFI][Windows 保留][E 盘 NTFS 603.6G][未分配 200GiB][Ubuntu ext4 150G]
```

目标结构是：

```text
[EFI][Windows 保留][E 盘 NTFS 603.6G][Ubuntu ext4 350G]
```

未分配空间位于根分区的**左侧**，而根分区原本只向右延伸。要利用左侧空间，就必须把 `p4` 的起点向左移动 200GiB，同时把分区总大小增加到约 350GiB。

这不是只修改分区表里的一个结束位置。分区起点变化后，原来的文件系统数据需要被搬移到新的物理位置。移动过程中如果断电或强制重启，可能同时破坏分区与文件系统。

另外，正在运行的 Ubuntu 不能可靠地移动自己的根分区。根文件系统始终处于挂载和使用状态，因此需要从 U 盘启动一个独立的 GParted Live 环境，让硬盘上的根分区保持未挂载状态，再进行调整。

所以这次操作的本质是：**离线移动根分区，并在移动后扩展 ext4 文件系统**，而不是“格式化一个新分区再挂上去”。

## 四、备份必须放到另一块物理盘

备份目标是 `/home/kkka`，最终归档文件为：

```text
/mnt/data/home_20261128.tar
```

`/mnt/data` 对应 `/dev/nvme0n1p4`，也就是 Windows 的 Data/D 盘。它是另一块物理 SSD 上的 NTFS 分区，容量 174.7G，当时已用约 29G、可用约 147G，足够容纳这次的备份。

这里我特意没有把备份放到 E 盘。E 盘和 Ubuntu 根分区都位于 `nvme1n1`，如果分区操作把这块盘的分区结构弄坏，同盘上的备份也可能一起不可用。**备份和源数据处在同一块物理盘上，只能防误删，不能充分防分区事故。**

备份方式使用 `tar` 归档，而不是把 Linux 家目录逐文件复制到 NTFS。原因是 Linux 家目录里存在符号链接、权限、ACL 和扩展属性等元数据；直接复制到 Windows 文件系统，容易在这些细节上丢信息。把它们先封装进一个 tar 文件，再由 NTFS 保存这个普通大文件，更符合这次的需求。

备份时通过 `--checkpoint=200` 输出连续的点作为进度提示。完成后，归档约 33G，成员数为 405002：

```bash
tar -tf /mnt/data/home_20261128.tar | wc -l
```

```text
405002
```

我还做了归档与当前文件的对比检查。检查过程中出现了一些 Chrome、微信、钉钉、Trae 和输入法相关文件的差异，因为备份后这些应用仍在运行，缓存、数据库和临时文件会继续变化。这类差异不等于备份损坏。

真正需要警惕的是下面这类读取错误：

```text
Unexpected EOF
Cannot open
Read error
```

本次没有出现 `Unexpected EOF`，归档可以完整读取，关键目录也存在于归档中。由此确认这份备份可用于恢复用户数据。

需要说明的是，**tar 备份 `/home` 不是整盘快照**。它主要保护用户数据，并不意味着根分区中的整个操作系统都能靠它原样恢复。因此，分区操作本身仍然必须谨慎，不能因为“有备份”就跳过设备核对。

## 五、制作 GParted Live U 盘：ISO、写盘和回读校验

使用的镜像是：

```text
gparted-live-1.8.1-6-amd64.iso
```

下载后的 ISO 约 687M，`file` 能识别为可启动的 `ISO 9660` 镜像，并带有 `GParted Live` 标识。仅把 ISO 当作普通文件复制到 U 盘并不等于制作启动盘，需要把镜像写入 U 盘设备。

目标 U 盘在 Linux 中识别为 `/dev/sda`，容量 58.6G。写入对象是整块设备 `/dev/sda`，不是硬盘 `/dev/nvme1n1`，也不是随意猜出来的某个分区。写镜像会覆盖 U 盘原有内容，所以执行前必须再次确认设备路径。

写入后，我没有只看 `dd` 是否返回成功，而是回读 U 盘前 687MiB，与 ISO 做 SHA-256 对比。两边结果完全一致：

```text
d789c38779f0d6f7026c12f44c2c52a04f66e28a1aea7d51f3045ad1bbf28411
```

这一步很有价值：分区调整本身就依赖 Live 环境稳定运行，如果启动 U 盘里的数据已经写坏，后面排查会多出一个没有必要的变量。

### 下载过程并不顺利

GParted 镜像托管在 SourceForge。命令行下载时出现过单连接速度很低、进度重新从 1% 开始，以及下面两个镜像域名解析失败的情况：

```text
nchc.dl.sourceforge.net
tds.dl.sourceforge.net
```

中间还尝试过切换镜像、`aria2` 续传和代理。最后通过浏览器下载成功。这个插曲和分区技术本身无关，但也说明镜像到手后检查大小、文件类型和写盘哈希是有必要的，不能默认“下载完成”就等于“文件完整”。

### U 盘的“输入/输出错误”不一定是硬件坏了

制作启动盘前，U 盘复制文件时出现过：

```text
输入/输出错误
```

一开始很容易直接判断为 U 盘硬件损坏，但进一步检查后发现，日志主要是：

```text
FAT-fs ... corrupted directory
```

同时存在未正常卸载、目录损坏等信息。普通用户直接执行 `dmesg` 时还遇到了“读取内核缓冲区失败：不允许的操作”，改用 `sudo dmesg` 后才能查看内核日志。

随后对 U 盘做了 300MB 顺序读取测试，速度约 27.3MB/s，没有出现硬件层面的 I/O error。因此最后判断这次更像 FAT32 文件系统损坏，而不是设备完全不可读。我确认 U 盘中没有需要保留的内容后，跳过了 U 盘文件备份，直接写入 ISO；写盘会覆盖原有 FAT32 文件系统，之后再通过整段回读哈希验证写入结果。

## 六、真正修改分区：在 GParted 中左移并扩展 `p4`

准备完成后，关机并从 GParted Live U 盘启动。整个关键操作只针对 `/dev/nvme1n1` 上的 `p4`，不碰另一块盘，也不修改 E 盘。

在 GParted 中，先通过右上角设备列表选择 `nvme1n1`，确认看到的是这次的分区布局。然后选中 `nvme1n1p4`，进入“调整大小/移动”，不要凭鼠标拖动的视觉效果估算大小，而是直接填写数值：

```text
Free space preceding = 0
New size             = 358400 MiB
Free space following = 0
```

`358400 MiB` 就是 `350 × 1024 MiB`，对应目标根分区大小 350GiB。将前置空闲空间设为 0，意味着把原本位于分区前面的 200GiB 空闲空间纳入这次调整；同时扩大分区并消除后置空闲空间。

点击应用前，我核对了下面几项：

1. 当前磁盘是 `nvme1n1`，不是保存 D 盘备份的 `nvme0n1`。
2. 操作对象是 `p4`，不是 EFI 分区，也不是 NTFS 的 `p3`。
3. E 盘仍为 603.6G，没有删除、格式化或新建分区的操作。
4. 根分区目标大小为约 350GiB，操作内容包含移动与扩展，而不是重新创建文件系统。
5. 已确认备份存在且能读取，电脑接通电源，操作期间不会主动中断。

确认后才点击 Apply。移动分区的过程中不能强制关机，也不要因为进度显示长时间不变就随意重启。

GParted 完成了分区移动和 ext4 文件系统扩展，所以回到 Ubuntu 后不需要再手动执行 `resize2fs`。这次也没有删除 swap 分区，因为系统使用的是 swap 文件，并不存在挡在空闲空间与根分区之间的独立 swap 分区。

## 七、扩容后的验证：分区变大，文件系统也要一起变大

完成操作后移除 U 盘，重新启动 Ubuntu。系统能够正常进入，`/home/kkka` 下的文档、下载、桌面和项目等原有目录都在。

`lsblk` 和 `df -h` 给出的关键结果为：

```text
/dev/nvme1n1p4  344G  96G  231G  30%  /
nvme1n1p3       603.6G
nvme1n1p4       350G  /
```

这几行分别说明：

- 根分区 `nvme1n1p4` 已经从 150G 变为 350G。
- 挂载在 `/` 上的 ext4 文件系统也已经扩展，可用空间从扩容前的约 45G 增加到 231G。
- E 盘对应的 `nvme1n1p3` 仍为 603.6G，没有被这次操作改写。
- 原有用户目录仍在，系统可以正常启动。

有人可能会问：为什么 `lsblk` 显示 350G，而 `df` 显示总容量 344G？这不代表少了 6G，也不代表扩容失败。`lsblk` 展示的是分区设备大小，`df` 展示的是文件系统可用视角下的容量；ext4 自身需要元数据区域，两者本来就不会完全相同。

这次分区移动后 UUID 保持不变，因此依赖 UUID 的挂载关系不需要因为“左移了 200GiB”而重写，也不需要重装系统。后续只需正常使用，并确认 Windows、Ubuntu 和重要文件都没有异常。

## 八、哪些时候可以停，哪些时候不能停

这次准备工作中途刚好遇到下班，需要暂停。我重新核对后发现，当时只完成了备份和启动盘制作，还没有在 GParted 中点击 Apply，硬盘分区尚未发生任何修改，因此可以安全停止。

离开前做了几件事：

- 对备份数据执行 `sync`，确保缓存落盘。
- 卸载 `/mnt/data`，避免 NTFS 分区带着未正常卸载状态离开。
- 关机，下午回来后重新检查分区、ISO、启动 U 盘和备份文件，再继续操作。

真正不能随意暂停的是 GParted 已经应用了移动分区任务之后。点击 Apply 前，所有排队操作都还可以重新检查；开始移动数据后，就不能把“关机”当作普通的暂停按钮。

如果操作结果不符合预期，也不应该立刻格式化或继续尝试其他写操作。应先保留现场，从 Live 环境检查分区和文件系统状态，再决定修复或恢复。对这类任务来说，知道什么时候不写磁盘，和知道该执行什么命令同样重要。

## 九、备份什么时候删除，启动 U 盘怎么处理

扩容成功后，D 盘根目录下会保留一个约 33G 的文件：

```text
home_20261128.tar
```

它在 Linux 中对应：

```text
/mnt/data/home_20261128.tar
```

这份备份没有必要在刚看到 `df` 变大后立刻删除。更稳妥的做法是再正常使用一两天，确认 Ubuntu 能稳定重启、重要文件可以打开、Windows 也能正常启动，然后再清理。

清理时只删除这一个 tar 文件，不要动 D 盘里的其他内容。GParted 启动 U 盘可以保留，也可以确认不再需要后重新格式化为普通存储盘；这属于收尾工作，不影响已经完成的扩容。

## 十、这次操作留下的检查清单

把整个过程压缩成一张顺序表，就是：

```text
记录原分区布局与 UUID
→ 在 Windows 中缩小 E 盘，保留未分配空间
→ 把 /home 用 tar 备份到另一块物理盘
→ 检查 tar 能完整读取并确认关键内容存在
→ 下载并验证 GParted Live ISO
→ 写入正确的 U 盘设备，回读并比较 SHA-256
→ 关机，从 U 盘启动
→ 选择 nvme1n1，左移并扩展 p4 到 358400 MiB
→ 检查操作清单后 Apply，等待完成
→ 回到 Ubuntu，用 lsblk、df 和用户文件共同验证
→ 稳定使用后清理备份，按需恢复 U 盘
```

其中有四条我会一直保留为分区操作的硬规则：

1. **先看物理盘和分区布局，再谈命令。** 不根据盘符和印象猜设备。
2. **备份放到另一块物理盘，并实际读取校验。** 文件存在不等于备份可用。
3. **Live 启动盘也要验证。** ISO 完整和 U 盘写入正确是两件事。
4. **Apply 前反复核对，Apply 后不要中断。** 尤其是移动根分区这种会搬移大量数据的操作。

## 小结

这次扩容表面上只是把 150G 变成 350G，实际最关键的是理解了分区位置：从 Windows E 盘压缩出来的 200GiB 位于 Ubuntu 根分区左侧，因此不能只扩展分区末尾，而要在离线环境中先左移再扩展。

方案上，我没有单独挂载一个新的 `/home`，而是让根分区统一使用这份空间，避免 Docker、系统软件和用户目录分别挤在不同的空间池里。安全上，备份放在另一块物理盘，用 tar 保留 Linux 元数据，又通过完整读取和成员统计确认归档可用；启动 U 盘则通过回读 SHA-256 排除了写盘损坏。

最终结果符合预期：根分区扩至 350G，文件系统可用空间同步增加，E 盘保持 603.6G，原有家目录仍在，不重装 Ubuntu，也不需要额外执行 `resize2fs`。真正值得复用的不是某一条命令，而是这套“先确认布局、再跨盘备份、离线操作、分层验证”的流程。
