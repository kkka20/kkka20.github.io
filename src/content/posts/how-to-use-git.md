Git 学习笔记：从本地仓库到团队协作

一个前端开发学生在学习 Git 过程中踩过的坑、记下的命令、悟出的道理

2026.09.18 · 个人笔记整理

学写代码的最初几天，我遇到过一个让人崩溃的场景：改了一下午的样式表，突然发现页面全乱了，想退回之前的版本，却发现自己把旧代码覆盖得干干净净。那天下班我做的第一件事，就是把 Git 装上。这篇文章是我学习 Git 过程中整理的全部笔记，从最基础的版本控制讲起，一直走到分支管理、远程协作和冲突处理。如果你也刚入门，希望它能帮你少走一些弯路。

第一步：让 Git 接管你的目录

Git 不会自动管理任何文件夹，你得先告诉它："这个目录归你管了。" 这一步叫初始化。进入你的项目目录，敲下第一条命令：

bash
# 初始化 Git 仓库
git init

执行完毕后，目录里会多出一个隐藏的 .git 文件夹，从这一刻起，Git 就开始默默追踪这个目录里的所有变化了。

但"追踪"不等于"管理"。你可以用 git status 随时检查文件状态——哪些文件是新增的、哪些被修改了。这个命令我几乎每次提交前都要敲一遍，它就像一个随时可以查看的待办清单：

bash
# 查看当前文件状态
git status

状态信息用颜色区分：红色表示文件有变动但 Git 还没管起来——可能是新增的文件，也可能是修改了的老文件；绿色则表示 Git 已经把它们纳入暂存区，准备生成新版本了。

要把文件纳入管理，需要用 git add 把它们放进暂存区。你可以逐个添加，也可以一把全收：

bash
# 添加指定文件到暂存区
git add 文件名
bash
# 添加所有文件到暂存区
git add .

暂存区就相当于一个"草稿箱"，你把要提交的内容放进去，确认无误后再生成一个正式版本：

bash
# 生成一个新版本
git commit -m "版本名"

-m 后面跟的是这次提交的描述信息，养成写清楚提交信息的习惯，未来的自己会感谢现在的你。

Git 的三区工作流——从工作目录到暂存区再到本地仓库：

时间旅行：查看与回滚历史

每次 commit 之后，Git 都会生成一个快照，你可以随时回到任何一个历史版本。查看提交记录用 git log：

bash
# 查看提交历史
git log

但 git log 有个局限：如果你做了 reset 回滚操作，被回滚掉的记录就从 log 里消失了。这时候 git reflog 就派上用场了——它记录了你的每一次操作，包括回滚本身，相当于一个"操作日志"：

bash
# 查看所有操作记录（包括已回滚的）
git reflog

当你需要查看分支的合并图形时，--graph 参数非常有用：

bash
# 查看分支图形
git log --graph

如果觉得输出太长，可以用简洁版，只显示版本号和提交信息：

bash
# 简洁版分支图形
git log --graph --pretty=format:"%h %s"

找到了目标版本号，就可以用 git reset 回到那个时间点：

bash
# 回滚到指定版本
git reset --hard 版本号

注意

--hard 会把工作目录里的文件也一起回滚到目标版本，当前未提交的修改会丢失。如果只是想看看旧版本而不丢弃当前修改，可以先用 git stash 暂存改动。

平行宇宙：分支的魅力

分支是 Git 最强大的特性之一。你可以从当前代码"分叉"出一条平行线，在里面大胆尝试新功能，完全不影响主线代码。创建一个新分支：

bash
# 创建新分支
git branch 分支名

查看当前仓库有哪些分支，带 * 号的是你当前所在的分支：

bash
# 查看所有分支
git branch

切换到另一个分支继续工作：

bash
# 切换分支
git checkout 分支名

当你在分支上完成了开发，需要把改动合并回主线时，先切换到 master 分支，再执行合并：

bash
# 合并前先切回 master
git checkout master
git merge 分支

小贴士

合并时可能会产生冲突——如果两个分支修改了同一行代码，Git 不知道该保留哪个版本，需要你手动解决。后面会专门讲冲突处理。

分支合并完成后，如果不再需要这个分支，可以删除它：

bash
# 删除分支
git branch -d 分支名
走向云端：与 GitHub 携手

本地仓库玩熟了之后，下一步就是把代码推到远程仓库。GitHub 是最流行的远程托管平台，它让你的代码有了云端备份，也让团队协作成为可能。

第一次把本地仓库连接到远程时，需要给远程仓库起个别名（通常叫 origin）：

bash
# 给远程仓库起别名
git remote add origin 远程仓库地址

然后就可以把代码推上去了：

bash
# 推送代码到远程
git push -u origin 分支

-u 参数会在本地分支和远程分支之间建立关联，以后直接 git push 就行，不用再写分支名。

如果是从零开始参与一个已有的项目，直接克隆整个仓库到本地：

bash
# 克隆远程仓库
git clone 远程仓库地址

git clone 会在本地生成一份完整的仓库副本，同时自动完成 git remote add origin 的操作，省去了手动关联的步骤。

当远程仓库有别人推送的新代码时，你需要拉取到本地：

bash
# 拉取远程更新
git pull origin 分支

下表汇总了本地与远程协作的常用命令：

场景	命令	说明
关联远程仓库	git remote add origin 地址	给远程仓库起别名
推送代码	git push -u origin 分支	首次推送并建立关联
克隆仓库	git clone 地址	下载完整仓库到本地
切换分支	git checkout 分支	切换到指定分支
拉取更新	git pull origin 分支	同步远程最新代码
让提交记录保持整洁：rebase

随着开发推进，提交记录可能变得杂乱：很多次细碎的 commit，回过头来看其实可以合并成一条。git rebase（变基）就是干这个的，它可以把多个提交记录压缩合并，让历史看起来干净利落。

bash
# 交互式 rebase，合并最近几条提交
git rebase -i HEAD~版本号

警告

合并提交记录时，不要合并已经 push 到远程仓库的代码。因为 rebase 会改写提交历史，如果别人已经基于你推送的版本做了开发，你 rebase 后再 push 会导致冲突和混乱。rebase 只在本地还没推送的提交上使用。

冲突不可怕

合并分支时遇到冲突是家常便饭——两个人改了同一个文件的同一行，Git 没法替你决定保留哪个，只能把两种内容都标出来让你手动选。

解决冲突最趁手的工具是 Beyond Compare。在 Git 中配置好之后，每次遇到冲突它会自动弹出可视化界面，左右对比一目了然。配置方法如下：

bash
# 配置 Beyond Compare 为默认合并工具
git config --local merge.tool bc3
git config --local mergetool.path '/usr/local/bin/bcomp'
git config --local mergetool.keepBackup false

配置完成后，遇到冲突时只需执行：

bash
# 启动 Beyond Compare 解决冲突
git mergetool

Beyond Compare 会打开一个分屏界面，左边是你的修改，右边是对方的修改，你可以逐行选择保留哪些内容。解决完所有冲突文件后，保存退出，再 git add 和 git commit 就完成了合并。

小贴士

keepBackup false 这个配置很关键，它让 Git 在解决冲突后自动清理 .orig 备份文件，不然你的目录里会堆满临时文件。

学会说"不"：忽略不需要管理的文件

项目里总有些文件不需要 Git 管理：编译产物、依赖包目录、IDE 配置文件、敏感的密钥文件等等。在项目根目录创建一个 .gitignore 文件，写上忽略规则，Git 就会自动跳过它们。

常见的忽略规则写法：

gitignore
# .gitignore 示例
# 忽略所有 .h 文件
*.h
# 但 a.h 不忽略（感叹号表示取反）
!a.h
# 忽略整个 files 目录
files/
# 忽略 .pyc、.pya、.pyd 等编译文件
*.py[c|a|d]

规则语法简洁但功能强大：* 是通配符，! 是取反（即"不要忽略"），[c|a|d] 是字符匹配集合。组合起来就能精确控制哪些文件该管、哪些不该管。

写在最后

回头来看这份笔记，从最初连 git init 都不知道敲什么，到现在能熟练地用分支管理功能开发、用 rebase 整理提交记录、用 Beyond Compare 搞定冲突——Git 的学习曲线不算陡，但需要反复实践才能形成肌肉记忆。

如果你也在学 Git，我的建议是：不要只看不练。建一个测试仓库，把上面的命令全敲一遍，亲手制造一次冲突再解决它，自己画一遍分支合并的图。当你把 add → commit → push 变成像呼吸一样自然的操作时，你就真正入门了。

工欲善其事，必先利其器。Git 就是那个器。
