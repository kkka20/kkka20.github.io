# 让巡检机器人"听懂"防空警报：一次可解释的声学事件识别实践

> 副标题：从"按音量判断"到"MFCC 指纹 + 四道物理门限"，含现场调参与实测数据
>
> 消防巡检机器人需要在巡逻途中识别防空警报并停车播报。本文基于 ROS 2 听觉节点，记录一套不依赖深度模型的声学事件识别方案：用 26 维 MFCC 指纹做整体音色匹配，再叠加谱集中度、主峰频带、扫频比三道物理门限压误报，最后用连续命中、冷却和半双工控制触发时机。文中给出各道门限的物理依据、现场实测数据，以及音量阈值、样本裁剪、余音窗口等踩坑记录。
>
> 运行环境：ROS 2 Jazzy + Python 3 + librosa + numpy，CPU 端实时运行，16kHz 单声道音频流。

## 1. 需求：巡检机器人为什么需要"耳朵"

消防巡检机器人的夜间任务是沿固定点位巡逻，检查灭火器、安全出口指示灯，以及是否有人违规吸烟。视觉之外，还有一类事件只能靠听：**防空警报**。

产品需求很明确：巡逻途中听到警报，立即停车、播报撤离提示、抓拍留证。

但把它拆成技术指标，就没那么轻松了：

- **不能漏**：真警报响起必须报；
- **不能误**：人说话、设备嗡鸣、环境噪声不能报；
- **要快**：警报是紧急事件，延迟不能以分钟计；
- **要能解释**：现场出问题时，工程师要能看懂是哪一维特征判错了。

这四条约束，决定了最终方案不能是一个"黑盒分类模型"。

## 2. 系统约束：麦克风共享、半双工、实时性

### 2.1 麦克风不是业务节点独占的

机器人头部的 8 阵麦克风被平台常驻音频进程占用。业务节点不能直接 `open()` 设备，只能：

1. 启动时调用平台的音频控制服务打开音频流；
2. 订阅平台输出的音频帧（16kHz / 单声道 / 16bit）；
3. 退出时再关流，把设备还给平台语音功能。

所以听觉节点的第一层设计是**音源可替换**：主路径走平台共享流，同时保留 `sounddevice` 直采 USB 麦克风的兜底路径。这样平台服务异常时，节点仍能降级工作，而不是直接失效。

### 2.2 半双工：别让自己的播报触发自己

头部麦克风和扬声器在同一个音频盒里，机器人一播报，自己就会听到自己。如果不处理，每一句 TTS 都可能触发一次"警报"。

方案是订阅一个播报状态话题：

- 播报中：暂停识别；
- 播报结束：再屏蔽 1.5s，等环形缓冲里的自身尾音流走；
- 额外设 60s 上限保护：万一"播报结束"消息丢失，最多静音 60s 后自动恢复，不会永久失聪。

### 2.3 实时性

音频帧持续到达，但判别必须限速。最终采用 **2s 滑窗 + 0.5s 步进**：

```
音频帧 → 环形缓冲(2s) → 每 0.5s 取整窗 → 特征 → 四道门 → 连续命中 → 警报
                                      ↑
                            播报状态 → 半双工屏蔽
```

窗口太短，扫频特征展不开；窗口太长，警报响了几秒才判断出来。2s 是这两个约束的折中。

## 3. 基线方案：音量阈值为什么一定会失败

最直觉的做法是算 RMS：

```python
rms = math.sqrt(sum(x * x for x in frame) / len(frame))
if rms > 0.025:
    fire_alert()
```

现场跑下来，两头都不对。

**漏检**：手机外放、距离远、音量偏小，真警报的 RMS 可能只有环境噪声水平，直接被门限杀掉。

**误报**：人凑近说话响度很大，照样过门。

更根本的问题是，**绝对 RMS 不是稳定特征**。麦克风增益、平台 AGC、风噪都会改变它。同一个警报在不同位置测出来的数值可以差一个数量级。

于是最终方案里，响度门只保留一个职责：**挡数字静音**。阈值 0.008，低于它说明几乎没有声音，直接跳过计算；被挡时也降频打日志，避免节点"静默运行"导致现场无法判断是安静还是故障。

> 教训：一个 0.025 的响度门，曾让整条链路连续几天没有任何输出。环境噪声本身就有 0.019，真警报几乎全被挡掉。**门限不只要"能挡误报"，还要保证"不挡真目标"**。

## 4. 方案总览：一条可解释的判别链

最终判别链分五层，每一层对应一个具体的物理差异。

**第一层，响度门 RMS**：区分"有声"和"几乎无声"，只挡数字静音，不做响度区分。

**第二层，MFCC 指纹相似度**：描述整体音色，负责挡掉大部分无关声音。相似度门槛 0.86。

**第三层，谱集中度**：区分窄带音和宽带音。警报能量集中在少数频点，人声和噪声摊在宽频带上。门槛 0.20。

**第四层，主峰频带**：区分中频和高频。警报主峰落在 300~3000Hz，机械啸叫在 4.5kHz 以上。这条门直接拒绝超出频带的声音。

**第五层，扫频比**：区分扫频音和稳态音。警报主峰持续移动，人声和嗡鸣几乎不动。门槛 1.40。

前四层逐帧判定，第五层在连续命中后计算。任意一帧掉门，连续计数清零。

关键设计原则：**每一道门都必须对应一个两类样本确实不同的维度**。如果两个类别在所有维度上都重叠，再精细的阈值搜索也只是拆东墙补西墙。

## 5. 特征设计：26 维 MFCC 指纹

### 5.1 为什么是 MFCC

MFCC 描述的是频谱包络，即"音色"。防空警报的频谱结构与语音、环境噪声差异明显，适合做整体匹配。

```python
def extract_mfcc(samples, sr):
    m = librosa.feature.mfcc(y=samples, sr=sr, n_mfcc=13)
    return np.concatenate([m.mean(axis=1), m.std(axis=1)])
```

13 个系数取时间均值（整体音色）和标准差（调制强度），拼成 26 维向量。匹配用余弦相似度，对幅度不敏感，只关心方向。

### 5.2 样本预处理：必须裁掉静音

样本是一段手机录制的真实警报，转成 16kHz 单声道。加载后第一件事是裁剪头尾静音：

```python
y_trimmed, (start, end) = librosa.effects.trim(
    y, top_db=18, frame_length=2048, hop_length=512)
```

不裁剪的话，静音帧会参与 MFCC 统计，把指纹"稀释"，同一段警报在不同裁剪方式下相似度会明显波动。裁剪后只保留有声主体段，匹配才稳定。

### 5.3 为什么不用 DTW 或深度模型

- **DTW**：对时间伸缩鲁棒，但计算量大，0.5s 一帧的实时性吃紧；
- **深度分类模型**：需要大量标注数据，这个场景只有一段样本；且模型输出不可解释，现场调参无从下手；
- **统计指纹 + 物理门限**：算力低、可解释、参数可现场微调。

对小样本、边缘端、需要现场可维护的场景，这是更现实的选择。

## 6. 三道物理门：把"像"变成"是"

MFCC 相似度在实验室表现很好，但现场立刻暴露问题：

> 真警报相似度 **0.866**，人声相似度 **0.864~0.888** —— 区间重叠。

这意味着单纯提高阈值，必然"压掉人声的同时也压掉真警报"。必须引入与 MFCC 正交的物理特征。

### 6.1 门 1：谱集中度 ≥ 0.20

警报是**窄带扫频音**，能量集中在少数频点上；语音和宽带噪声的能量摊在很宽的频带上。

```python
band = (freqs >= 300) & (freqs <= 3000)
Sb = np.abs(S[band]) ** 2
top3 = np.sort(Sb, axis=0)[-3:].sum(axis=0)
conc = (top3 / (Sb.sum(axis=0) + 1e-12)).mean()
```

计算 300~3000Hz 带内、每帧功率最大的 3 个频点占带内总功率的比例，再取时间平均。

实测：**警报样本 0.406，环境人声 0.084~0.091，差约 4.5 倍**。这是挡人声的主力门。

### 6.2 门 2：主峰频带 300~3000Hz

逐帧取全谱最大频点，统计命中窗口内的中位数：

```python
peaks = freqs[np.argmax(S, axis=0)]
peak_med = np.median(peaks)
```

警报扫频主峰落在 **398~2445Hz，中位 781Hz**。而户外误报源的声能量主峰在 **4.5~6kHz**，属于机械啸叫或高频告警器，即使相似度和谱集中度都过门，也会被这道门拒绝。

### 6.3 门 3：扫频比 ≥ 1.40

防空警报是**连续扫频**，主峰频率在窗口内持续移动；人说话、稳态嗡鸣的主峰几乎不动。

```python
def sweep_ratio(peaks):
    if len(peaks) < 2:
        return None
    low, high = min(peaks), max(peaks)
    return high / low
```

实测数据非常干净。真警报（现场外放）的主峰扫频比在 **1.42~1.98** 之间；现场一次人声误报窗口只有 **1.33**；稳态嗡鸣约为 **1.0**。

现场那次人声误报，前三道门全过、连续命中 5 帧，唯一破绽是扫频比只有 1.33。把门限从 1.30 微调到 1.40，正好卡在两者中间。

> 这道门是整篇文章最值得复用的经验：**当两个类别的某个特征区间重叠时，不要硬调那个特征，去找另一个区间不重叠的维度。**

## 7. 时间维度：连续命中、冷却与半双工

### 7.1 连续命中

单帧判定再稳，也会有偶然的擦线窗口。因此要求：

- 连续命中 **6 帧**，每帧 0.5s，即持续 3s；
- 任意一帧掉门，计数与扫频序列**全部清零**；
- 达到 6 帧后再计算扫频比，低于 1.40 直接放弃并清零。

人声是断续音节，相似度波动大，很难凑满连续 6 帧；真警报通常持续数十秒，不受影响。

### 7.2 冷却

触发后冷却 15s，防止同一段警报反复播报。

### 7.3 半双工实现

```python
def on_speaking(msg):
    if msg.data:
        mute_until = now + 60.0      # 上限保护
    else:
        mute_until = now + 1.5       # 余音窗口
```

窗口不能随意调大。早期设 2.5s，播报结束后马上响起的真警报会被余音窗口吞掉。1.5s 是"尾音流走"和"尽快恢复监听"的折中。

## 8. 实测数据与调参记录

### 8.1 最终参数

**采集部分**：采样率 16000Hz，与平台音频流一致；滑窗长度 2.0s；滑窗步进 0.5s。

**特征与门限**：响度门 0.008，只挡数字静音；MFCC 余弦相似度门槛 0.86；谱集中度门槛 0.20；主峰频带 300~3000Hz；扫频比门槛 1.40。

**时间维度**：连续命中 6 帧；触发冷却 15s；播报后余音屏蔽 1.5s。

所有参数都放在 yaml 里，现场不改代码、不重编译，直接调配置重启节点即可。

### 8.2 调参时间线

1. **初版**：MFCC 阈值 0.84，户外机械噪声擦线误报，相似度 0.851~0.855；
2. **提阈值**：0.84 提到 0.86，机械噪声被挡，但发现人声与真警报区间重叠，人声 0.864~0.888、真警报 0.866；
3. **加谱集中度**：人声 0.08~0.13，警报 0.406，人声误报大幅下降；
4. **加主峰频带**：挡住 4.5~6kHz 的高频啸叫；
5. **加扫频比**：1.30 提到 1.40，专门清理"前三门都过的擦线人声"；
6. **连续命中**：5 帧提到 6 帧，进一步压低断续人声。

每一步都不是"感觉好了"，而是先在日志里找到漏网的样本，再确认它在哪一维与真警报不同，最后才加门限。

### 8.3 踩坑清单

**第一个坑：把 RMS 当主判据**。后果是真警报几乎全漏，因为环境噪声本身就有 0.019，0.025 的门限把整条链路几乎打成静音。修正方式是让 RMS 只负责挡数字静音。

**第二个坑：只提高 MFCC 阈值**。后果是压掉误报的同时也压掉真警报，因为两类样本在该维度区间重叠。修正方式是引入正交的物理门限。

**第三个坑：样本不裁剪静音**。后果是指纹被稀释、匹配不稳。修正方式是加载时用 `librosa.effects.trim(top_db=18)` 裁掉头尾。

**第四个坑：余音窗口过长**。后果是播报刚结束的真警报被屏蔽窗口吞掉。修正方式是从 2.5s 缩到 1.5s。

**第五个坑：日志不降频**。后果是 0.5s 一帧刷屏，关键命中记录被淹没。修正方式是安静和屏蔽状态改为每 8 次打一条。

## 9. 工程细节：缓冲、日志与降级

### 9.1 环形缓冲

固定 2s 长度的 numpy 缓冲区，每来一帧就整体左移并写入新数据：

```python
self._ring = np.roll(self._ring, -n)
self._ring[-n:] = new_samples
```

`np.roll` 实现简单，但每次都有内存拷贝。2s × 16kHz 等于 32000 个 float32，单次拷贝约 128KB，0.5s 一次，开销可以接受；如果采样率更高，建议换成环形索引。

### 9.2 日志即调试界面

现场没有可视化，日志就是唯一的观测手段。因此每帧输出一行：

```
[audio] air_raid mfcc_sim=0.891 conc=0.512 peak=742Hz 扫频=1.76
        rolloff=3012Hz rms=0.041 阈值=0.86/0.20/1.40/300-3000Hz 连续=4
```

这一行里能同时看到四道门的当前值、连续计数，出问题时立刻判断是哪道门放行或拦截。安静和屏蔽状态则降频输出，保留心跳但不刷屏。

### 9.3 优雅降级

- 平台消息包不可见：报错并停止，不假装工作；
- 样本缺失：跳过该样本，若全部缺失则明确报错；
- 依赖库缺失：启动时给出明确安装提示；
- 音频回调里不抛异常：任何解码失败直接丢弃该帧。

原则是：**宁可明确报错，也不静默地"看起来在运行"**。

## 10. 局限与下一步

1. **没有声源方向**。头部 8 阵麦克风硬件支持 DOA，但平台输出的是 8 路混合后的单声道流，到达时间差信息已丢失，无法反推方向。若要做"朝声音方向走"，需要拿到分通道数据。
2. **确认延迟约 3s**。2s 窗口加 6 帧 × 0.5s。对"立即撤离"可以接受；对更紧急事件需缩短 hop 或降低连续命中数，代价是误报上升。
3. **事件扩展需要样本**。新增玻璃破碎、呼救声等事件，需要新样本并单独标定门限，不能套用警报参数。
4. **极端 AGC 下仍需复核**。频域特征比 RMS 抗增益，但不是完全免疫。

优先级：**分通道声源定位 → 频带能量归一化 → 多事件分类**。

## 11. 结语

这套听觉模块没有用任何深度学习模型，全部是可解释的统计特征和物理门限。它能在现场站得住，不是因为某个阈值调得准，而是因为每一道门都对应一个真实的物理差异：

- 窄带 vs 宽带，对应谱集中度；
- 中频 vs 高频，对应主峰频带；
- 扫频 vs 稳态，对应扫频比；
- 持续 vs 断续，对应连续命中。

调参的本质不是找"最佳阈值"，而是先找到能把两类样本分开的维度，再在那个维度上取中间值。
