# 八界杯机器人比赛复盘：运动学、逆解与三个差点漏过的坑

> 前言：八界杯（ecovacs-bajie）初赛交完之后，我把整个仓库重新过了一遍代码审查。本来以为答案都对了就没事，结果查出三个问题：一个是正解里万向锁分支写错但 demo 恰好没触发的 latent bug，一个是队友用错随机库导致 seed 对不上，还有一个是我自己没读代码就给了三条全错的建议。这篇把过程记下来，重点讲清楚"为什么答案看起来对、代码却可能是错的"。

运行环境：Ubuntu 24.04 + ROS 2 Humble + Isaac Sim + Docker

比赛是科沃斯办的八界杯，初赛三道题：题目一按阶段驱动机器人关节并在 RViz 展示，题目二给定关节值算末端位姿和坐标变换，题目三在 Isaac Sim 里用机械臂触碰三个玩具。三道题共用同一个机器人模型 `bajie_robot`，代码放在一个 ROS 2 工作区里提交。

## 一、先把三道题的代码结构理清楚

整个 `src/` 下四个包：

| 包                  | 作用                                            |
| ------------------- | ----------------------------------------------- |
| `bajie_robot`       | 官方 URDF 模型，只读，不能改                    |
| `question1_project` | 关节分步驱动，向 `/joint_states` 发数据         |
| `question2_project` | 正向运动学（FK），纯 numpy，没有 ROS 依赖       |
| `question3_project` | 逆运动学（IK）+ Isaac Sim 触碰，import Q2 的 FK |

依赖关系很清楚：Q3 不重复实现 FK，直接 `sys.path.insert` 后 `from fk_solver import forward_kinematics`。这条依赖链后面会引出一个代码审查的教训，先按下不表。

## 二、坑 1：FK 的万向锁分支写错了，但 demo 恰好没触发

题目二的 `fk_solver.py` 核心是 12 关节连乘，最后要把 4×4 旋转矩阵反解成 RPY。反解函数 `matrix_to_rpy` 有个万向锁分支——当 `pitch ≈ ±π/2` 时，`roll` 和 `yaw` 会退化到同一根轴上，常规公式失效，必须走特殊分支。

审查时我写了个重构测试：随机生成一组 RPY，转成矩阵再反解回来，看误差。结果：

```
常规情况重构误差：2.22e-16
万向锁重构误差：2.0          ← 完全错了
```

去看代码，万向锁分支写的是：

```python
r = math.atan2(R[1, 2], R[1, 1])
```

正确公式应该从矩阵的第一行恢复：pitch 为 `+π/2` 时 `R[0,1]=sin(r)`、`R[0,2]=cos(r)`，所以 `r = atan2(R[0,1], R[0,2])`；pitch 为 `-π/2` 时符号反过来。改完之后：

```
常规情况重构误差：2.78e-16
万向锁重构误差：2.78e-16   ← 修好了
近万向锁边界误差：4.94e-11
```

**最要命的地方在于**：当前公开测例的两个 case（`demo_zero` 全零关节、`demo_nonzero` 非零关节）算出来的 pitch 分别约是 0.0008 和 -0.63，都不触发万向锁。所以修复前的输出恰好是对的，评审跑公开测例完全看不出问题。只有评分方给了一个 pitch 接近 ±90° 的隐藏测例，RPY 和四元数才会彻底错乱。

这是个典型的 latent bug：**测试覆盖不到，不代表代码是对的**。我现在写任何旋转相关的代码，都会补一个"随机 RPY → 矩阵 → 反解"的重构自测，专门盯万向锁和近零旋转这两个退化点。

## 三、坑 2：seed 复现用错了随机库，输出差了一个数量级

题目一要求 `seed=7` 时输出与官方示例逐值一致。队友早期版本里采样用的是 `numpy.random`：

```python
rng = np.random.default_rng(seed)
val = rng.uniform(lo, hi)
```

跑出来 `lift_joint = 0.033576`，但官方示例是 `0.244767`。差了快一个数量级，而且不是四舍五入能解释的。

原因是 `numpy` 的伪随机数算法和 Python 标准库 `random` 完全是两套实现，同一个 `seed=7` 产出的序列根本不一样。官方示例是用标准库生成的，必须照抄：

```python
import random as _random
rng = _random.Random(seed)
val = float(rng.uniform(lo, hi))
```

改完 `lift_joint` 立刻对上 `0.244767`，后面所有关节值也逐值一致。

还有一个容易踩的点是**采样顺序**。`random.Random` 是状态机，`generate_phase_targets` 里必须严格按 `lift_joint → pitch_joint → joint1..6 → finger_open` 的顺序抽，少抽一次或者顺序换了，后面所有值全错。代码里的 `TARGET_RANGES` 也不是随便定的，是按官方示例反推出来的窄范围。

教训：**凡是要求"给定 seed 复现"的题，先搞清楚对方用的是哪套 RNG**。Python 标准库、numpy、C++ 的 `std::mt19937`，同 seed 不同库，结果天差地别。

## 四、题目三：DLS 逆解和"只信 PhysX 不信猜测"

题目三是技术含量最高的一题。给定 `objects_link` 的目标位姿，求 7 个关节（升降 + 机械臂 6 轴）的角度，让夹爪碰到玩具。

逆解用的是阻尼最小二乘（DLS），数值雅可比：

```python
# 每个关节 +1e-6，看误差怎么变，凑出 6×7 的雅可比
J[:, i] = (pose_error(fk(q + eps * e_i)) - e) / eps
# 阻尼最小二乘：dq = -J^T (J J^T + λ² I)^-1 e
dq = -J.T @ np.linalg.solve(J @ J.T + lam ** 2 * np.eye(6), e)
```

这里的 `λ² I` 是灵魂。机械臂接近奇异位形（伸直或折叠）时，普通最小二乘会炸出极大的关节步长，DLS 用阻尼换稳定。这是 KDL、TRAC-IK 这些工业 IK 求解器都在用的思路。

但比逆解更关键的是**接触判定**。一开始很容易想当然：夹爪末端位置和玩具位置距离小于某个阈值，就算碰到了。这个做法在仿真里不靠谱——玩具可能被夹爪推走但没真正接触，也可能模型穿插了但物理引擎没报接触。

最后用的方案是**订阅 PhysX 的接触报告**：

```python
# 给指尖连杆和所有玩具打上 ContactReport 标记
PhysxSchema.PhysxContactReportAPI.Apply(prim).CreateThresholdAttr(0.)

# 回调里只认一种情况：actor 对里同时有指尖和目标玩具，且 separation <= 0
if fingers and toys and point.separation <= 0:
    self.touch = info
```

只有 PhysX 报了接触、分离量为负，才算真碰到。下探过程中还加了护栏：玩具被推动超过 8 mm 或倾角超过 0.06 弧度就停，避免没碰到却把玩具撞飞。

这段代码后来还修了两个 bug：`--scene` 参数在模块导入时就解析（参数还没解析就提前退出）、没碰到玩具仍然正常写出答案（应该终止）。都是审查时发现的。

## 五、坑 3：我自己没读代码，给了三条全错的建议

这是最该记下来的一条，因为犯错的是我自己。

审查题目三时我凭印象给了三条"优化建议"：删掉输出里的 `name` 字段、把日志裁成只留 `[q3]` 行、删掉 `package.xml` 里的 `<exec_depend>question2_project</exec_depend>`。队友 dsh 看完直接反驳，三条全错：

1. **删 `name`**：`touch_toys.py` 里是 `"name": case.get("name")`，输入有 name 就透传 name。删输出不如删代码，而且输入文件本来就带 name。
2. **裁日志**：官方 README 明确要求 `assets/` 下提交完整的 `.log`，这是合规项不是可选优化，裁了等于把修好的东西改坏。
3. **删 `exec_depend`**：`touch_toys.py` 和 `ik_solver.py` 真的在 `sys.path.insert` 后 `from fk_solver import ...`，`exec_depend` 是保证 colcon 构建顺序的正确声明。删了清单和代码不符。

三条全错，根因是同一个：**我没读代码，凭 JSON 结构和主观感觉给建议**。正确的顺序应该是先列"不能动"的（评分硬性要求、代码真实依赖、提交契约），再列"能优化"的，最后才给建议。我反过来了，直接跳到了第三步。

dsh 反建议全对，本质上都是把"读代码确认依赖链"这一步做了。这条教训比任何技术点都重要：**给"删东西"的建议之前，先打开相关文件的 import 链和输出链，确认删了不会断；再看规范文档，确认删了不违规**。

## 六、两个工程上的小问题，顺手记一下

审查还扫出两个不影响答案但影响交付质量的点：

- **贡献者统计**：仓库 35 个提交用的邮箱没绑定到 AtomGit 账号，贡献者列表只显示 1 个人。在账号设置的邮箱管理里补上提交邮箱并验证，历史提交会自动回溯归属，不用改代码强推。
- **两个 `src` 目录**：仓库根下的 `单焱坤+安家兴/src` 是交付版（git 跟踪），`bajie_ws/src` 是本地 colcon 工作区副本（不进 git）。改代码只能改交付版，再同步到工作区编译，反过来改会丢。

## 小结

这次比赛做完，回头看最值钱的三样东西：

一是**一套验证过的旋转转换代码**。`rpy_to_matrix`、`matrix_to_rpy`、`matrix_to_quat_xyzw` 这三个函数，任何机器人、视觉、自动驾驶项目每天都会用到，网上抄来的实现十有八九万向锁和四元数分支是错的。手里有一份跑过重构自测的正确版本，比什么都管用。

二是**对"答案对但代码错"的警惕**。公开测例过了不代表隐藏测例能过，latent bug 最危险。写完运动学相关代码，补一个随机参数的重构自测，成本很低，收益很高。

三是**代码审查要先读代码再说话**。我自己栽在这上面，三条建议全错。以后给任何"删东西"的建议，先确认 import 链不断、规范文档不违规，再开口。

比赛结束了，但这几条教训会跟着后面所有的项目走。
